# infacilityMAP 設計メモ

このリポジトリが何を目指していて、そのためにどう作られているか。
コードを読む前に一度目を通すと、どこを触ればいいかが分かるようにしてある。

---

## 1. 目的

**GPSの届かない屋内で、初めて来た人を目的の部屋まで連れていく。**

解こうとしている状況はかなり限定されている。

- 校舎・施設の来訪者。建物の構造を知らない。
- アプリを入れてもらえない。その場で使い始めてもらう必要がある。
- 屋内なのでGPSは使えない。測位インフラ（ビーコン等）も置けない。
- 地図を作るのは開発者ではなく、施設の人。プログラミングはしない。

ここから、設計上ゆずれない条件が決まる。

| 条件 | 理由 |
|---|---|
| **Webで動く** | インストールを要求できない。QRを読んだらその場で開く必要がある |
| **現在地はQRで決める** | 屋内測位がないので、出発点は人手で確定させるしかない |
| **地図はGUIで作れる** | 施設の人がメンテナンスする。JSONを手書きさせない |
| **センサーは「あれば使う」** | 端末によって気圧計もコンパスもない。なくても動くこと |

### やらないこと

- 高精度な屋内測位。歩数からの推測航法＋チェックポイントでの補正までとする。
- 不特定多数の施設への汎用対応。マップは `config.dart` に手で登録する。
- サーバ。マップは静的アセットとして配る。

## 2. 全体の流れ

```
 ifmap_editor (PC)                    ifmap (スマホ / Web)
 ─────────────────                    ────────────────────
 見取り図を読み込む
        │
        ▼
 マウスで塗る
   通路 / 部屋 / 階段 / 接続点 / 屋外
        │
        ▼
 JSON出力 ──────────────►  ifmap/assets/<建物>/<フロア>.json
                                      │
                                      ▼
                            config.dart の mapSections に登録
                                      │
                                      ▼
                            QRで現在地確定 → ダイクストラ法で経路
                                      │
                                      ▼
                            歩数で現在地を進め、
                            チェックポイントで補正
```

### 2つのプロジェクト

| | 役割 | 動かす場所 |
|---|---|---|
| `ifmap_editor` | 見取り図からマップJSONを作る | PC (Windows / macOS / Chrome) |
| `ifmap` | 利用者が使うナビゲーション | スマホのブラウザ / Android / iOS |

両者をつなぐのは**JSONの形だけ**で、コードは共有していない。
そのぶん、形が食い違うと実機で初めて壊れているのが分かる。
そこを塞ぐために `ifmap/test/real_asset_smoke_test.dart` が実データを読んで検査している。

## 3. データの形

エディタが書き出すJSONは、1フロア＝1ファイル。

```jsonc
{
  "node_{行}-{列}": {
    "x": 列 * 10,          // JSON-px。マスの左上
    "y": 行 * 10,
    "edges": ["node_..."],  // 壁を挟まずに行き来できる隣のマス
    "name": "情報工学科棟1F 電算室",
    "isStairs": true,       // 階段
    "isConnector": true,    // 別棟・別フロアへの接続点
    "connectsToMap": "NITTC_2F",
    "isOutdoor": true,
    "wallTop": true, "doorRight": true  // …
  },
  "_editorData": {
    "bgImageBase64": "...",  // エディタの再表示用。ifmap は読まない
    "cells":  [{"x": 列, "y": 行, "type": 3, "name": "..."}],
    "rooms":  [{"name": "...", "centerX": 0, "centerY": 0}]
  }
}
```

### 座標と単位

ここが全部の数値のもとになる。

| | 値 | 定義場所 |
|---|---|---|
| 1マスの描画px (JSON-px) | 10 | `AppConfig.pxPerCell` |
| 1マスの実距離 | 0.5 m | `AppConfig.metersPerCell` |
| 1 JSON-px の実距離 | 0.05 m | `AppConfig.metersPerPx`（上2つから計算） |
| 平均歩幅 | 0.7 m = 14 JSON-px | `AppConfig.strideMeters` |

`metersPerCell` は **ifmap と ifmap_editor の両方に同じ値で置いてある**。
ずれると残り距離表示と歩数換算がまとめて狂うので、変えるときは必ず両方。

### セル種別 (`type`)

`lib/data/map_data.dart` の `CellType` と、エディタの `MapCell.type` が対応する。

| 値 | 意味 |
|---|---|
| 0 | 空白（歩けない） |
| 1 | 通路 |
| 3 | 目的地 / QR設置場所 |
| 4 | 階段 |
| 5 | 接続点（別棟・別フロアへ） |
| 6 | 屋外 |
| 10 | 装飾（建物外観など） |

> **落とし穴**: エディタは `type` を `_editorData.cells` にしか書き出さず、
> ノード側には出さない。ifmap は読み込み時に `node_{行}-{列}` をキーに
> セルの `type` をノードへ写し込んでいる（`parseFloorJson`）。
> ここが切れると「部屋に入る/出る」のチェックポイントが静かに消える。

## 4. ifmap の構成

```
lib/
  main.dart                       アプリの起動だけ
  config.dart                     定数・マップ一覧・設定トグル
  data/
    map_data.dart                 JSON読み込み、索引づくり、名前解決
  routing/
    route_calculator.dart         1フロア内のダイクストラ法
    route_planner.dart            階をまたぐ経路の組み立て
  sensors/
    step_tracker.dart             歩数→経路上の位置、気圧、GPS、チェックポイント
    heading_source*.dart          方位角（ネイティブ/Webで実装を差し替え）
  navigation/
    navigation_controller.dart    ナビの状態すべて。UIはこれを見るだけ
    suggestion_policy.dart        「いつ提案を出すか」だけの純粋ロジック
    route_geometry.dart           経路を線として扱う（ならした表示線・進んだ点・進む向き）
    route_guide.dart              曲がり角・チェックポイントから「次にすること」を組み立てる
  ui/
    map_screen.dart               画面の組み立てと、カメラをどこへ向けるか
    theme.dart                    色と文字の決まりごと
    place_category.dart           部屋名から種類（色・アイコン）を推し量る、検索の表記ゆれ
    format.dart                   距離・時間の表記、案内のアイコン
    search_screen.dart            場所の検索
    qr_scanner_screen.dart        QRスキャン
    sensor_debug_sheet.dart       実機での切り分け用（メニュー > センサー診断）
    map/
      floor_geometry.dart         マス目 → 部屋の輪郭・壁・扉（フロアごとに1回だけ作る）
      map_camera.dart             カメラ（中心・ズーム・回転）とアニメーション
      map_viewport.dart           指の操作（移動・ピンチ・回転・ダブルタップ）
      map_painter.dart            描画
    widgets/
      map_overlays.dart           検索欄・階の切り替え・丸ボタン・提案カードなど
      nav_banner.dart             案内中の「次にすること」
      sheets.dart                 下のシートの中身（状況ごと）
```

### 画面の組み立て

地図を全画面に出し、UIはすべてその上に浮かべる（Google マップと同じ考え方）。

| 場所 | 出すもの |
|---|---|
| 上 | 検索欄と分類チップ。経路の確認中は「出発 → 目的地」、案内中は「次にすること」 |
| 右 | 階の切り替え（自分のいる階に青、目的地の階に赤の点）。回転中は方位磁針 |
| 右下 | 現在地ボタン。押すと追従、追従中にもう一度押すと「進む方向を上」と切り替え |
| 下のシート | 状況ごとの中身。現在地を設定 → 場所の情報 → 経路の確認 → 案内中 → 到着 |

### 地図の描き方

エディタのマスをそのまま四角で塗ると「ドット絵」になるので、
`FloorGeometry` が同じ部屋のマスをまとめて外周をたどり（輪郭追跡）、
1マスずつの段々を Douglas-Peucker でならした図形にしている。
壁と扉はノードの印から線分を作り、一直線に並ぶものはつなぐ。
部屋の色とアイコンは名前（「講義室」「トイレ」「階段」など）から推し量る。

部屋名・アイコン・ピン・現在地は画面座標で描く。地図を回しても文字は水平、
拡大しても同じ大きさで、重なるものは優先度の低いほう（狭い部屋）を出さない。

どこともつながっていない名前のない小さな塊（図の四隅の位置合わせの印など）は
描かず、全体表示の範囲にも含めない。

### 状態の持ち方

`NavigationController` (ChangeNotifier) が全部持ち、UIは購読するだけ。
更新の流し方を2つに分けている。

- **`notifyListeners()`** … 経路・目的地・フロアなど、画面の構造が変わるもの。
- **`ValueNotifier`** … 現在地・方位・進んだ距離など、毎秒何度も来るもの。
  `ValueListenableBuilder` で必要な部分だけ描き直す。
  センサー1イベントごとに画面全体を作り直さないため。

### 場所の指し方

部屋は **必ず `PlaceRef(name, label)` でフロアとセットで扱う**。
「トイレ」のように同じ名前が複数フロアにある以上、名前だけでは足りない。

## 5. 現在地をどう出しているか

屋内測位がないので、次の順で「確からしさ」を積み上げている。

1. **QRで出発点を確定する**（`?start=<ノード名>` またはカメラ）。
   ここだけは誤差ゼロ。
2. **歩数×歩幅で経路上を進める**（`StepTracker`）。
   経路から外れる前提を置かず、**経路上の1次元の位置**としてだけ扱う。
   2次元で自由に動かすと、方位の誤差がそのまま位置の誤差になるため。
3. **チェックポイントで補正する**。
   部屋の出入口・扉・屋外との境目にゲートを置き、ユーザーがタップするまで
   歩数はそこで止まる。タップされた時点で位置を確定させる。
4. **気圧で階の移動を検知する**（あれば）。相対高度が 2.5 m 超で提案を出す。
5. **GPSで建物の接近を検知する**（屋外のみ）。20 m 以内で提案を出す。

4と5は**提案までしかしない**。自動で切り替えると、誤検知したときに
ユーザーが何が起きたか分からなくなる。

---

## 6. 通知の出し分け

歩きながら見る画面なので、割り込みの強さを3段階に分けてある。

| 種類 | 何に使うか | 操作を止めるか |
|---|---|---|
| **トースト** | 結果の報告（現在地を設定した、など） | 止めない。放っておくと消える |
| **提案カード** | 提案（階を移動した？ 別の建物に来た？） | 止めない。画面の上に残る |
| **到着シート** | 到着したとき | 下のシートが到着の表示に変わる。「完了」で着いた場所が現在地になる |

提案を出しすぎないためのしくみは `SuggestionPolicy` に集めてある。

- **クールダウン** (20秒) … 直前の提案から一定時間は何も出さない。
- **スヌーズ** (5分) … 「あとで」を押された提案はしばらく出し直さない。
  以前は永久に出なくなっていたが、それだと建物に入り直しても反応しなくなる。
- **ヒステリシス** … GPSは 20 m で提案し、40 m 離れるまで再武装しない。
  境界を行ったり来たりしても出続けない。

センサーの生イベントをそのままUIにつなぐとここが全部崩れるので、
判定は必ず `SuggestionPolicy` を通す（テストは `test/suggestion_policy_test.dart`）。

## 7. 階をまたぐ経路

`RoutePlanner` が、フロアを1枚ずつ「入口→出口」でつないでいく。

```
1F: 出発地 ──► 1F/2F の接続点（なければ階段）
2F: 上がってきた地点 ──► 2F/3F の接続点
3F: 上がってきた地点 ──► 目的地
```

またぎ方は2通り。

- **接続点** (`isConnector`)：エディタで `connectsToMap` を指定したもの。
  行き先が明示されているので最優先。
- **階段** (`isStairs`)：接続点がないときの代替。
  **両フロアで `name` が一致する階段**を同じ階段とみなす。
  つまり階段には両フロアで同じ名前を付けること。

全フロア分の経路を一度に計算して `floorPaths` に持つので、
表示フロアを切り替えても再計算は要らない。

## 8. 既知の弱点と、次にやるとよいこと

優先度順。

### (0) 同じ階の別の棟へ経路が出ない — 影響大

NITTC_1F は棟ごとに通路が分かれていて、たとえば 211講義室 から同じ 1F の中で
たどり着ける部屋は 85 室中 26 室しかない（111講義室 などへは行けない）。
実際には屋外（NITTC_ground_1F）や別の階を通れば行けるはずだが、
`RoutePlanner` は出発と目的地が同じ階なら、その階の中だけを探す。

直すには、同じ建物の全フロアと屋外図を1つのグラフとして探す必要がある。
ただし経路が「1F → 屋外 → 1F」のように同じ階を2回通ると、
いまの `floorPaths`（フロア → ノードの並び）では表せないので、
経路を「区間の並び」で持つように変えることになる（トラッカーと画面も合わせて）。
画面は「この2か所をつなぐ通路がマップ上に見つかりませんでした」と出す。

### (1) アセットが重い — 影響大

現状 `ifmap/assets/` は **約 15 MB**。Web版は起動のたびにこれを
ダウンロードしてJSONパースする。Flutter 3.41 でオフラインキャッシュ用の
Service Worker は廃止されたため、頼れるのはブラウザのHTTPキャッシュだけ。

内訳と対策:

- **`bgImageBase64` が約 5.6 MB**。エディタの再表示用で、ifmap は一度も読まない。
  `dart run tool/strip_bg_image.dart --apply` で消せる（15 MB → 9.3 MB）。
  ただし消すとエディタで読み直しても見取り図が出ないので、
  編集を続けるなら元ファイルを別に残すこと。
- **残りはノードとセルの重複**。`node_{行}-{列}` は
  `x`/`y` と `edges` を文字列で持っていて、同じ情報がセル側にもある。
  NITTC_1F だけでノード 20,946 / セル 27,349。
  edges は壁・扉の情報から実行時に導けるので、セルだけを配って
  グラフを起動時に組み立てれば、素直に半分以下になるはず。
  ただしエディタの出力形式を変えることになるので、対応は両側同時に。

### (2) フロアを全部先読みしている

`MapRepository.loadAll()` は起動時に全フロアを読む。
いまは1枚ずつ `await` を挟んで進捗を出しているので固まりはしないが、
使わないフロアまで読んでいることに変わりはない。

遅延読み込みにするには「どの名前がどのフロアにあるか」を
パース前に知る必要がある。軽い索引ファイルを別に書き出すのが素直。

### (3) `ifmap_editor` にテストがない

CI (`.github/workflows/ci.yml`) は `test/` があれば回すようになっているので、
書けばそのまま動く。JSONの書き出し形式は ifmap 側と対になっているので、
`JsonExporter` の出力が `parseFloorJson` で読めることを確かめる1本が効く。

### (4) 歩幅が固定値

`AppConfig.strideMeters = 0.7`。人によって2割は違う。
チェックポイント間の実測歩数から自動で較正できるはず
（ゲート間の距離は分かっているので、そこまでに何歩かかったかを見ればよい）。

### (5) センサー設定が保存されない

`AppSettings` はメモリ上だけなので、アプリを開き直すと既定値に戻る。
気圧計のない端末では毎回オフにし直すことになる。

## 9. 開発するときに

```bash
# ナビゲーションアプリ
cd ifmap
flutter pub get
flutter analyze && flutter test
flutter run -d chrome

# エディタ
cd ifmap_editor
flutter pub get
flutter run -d windows   # または -d chrome, -d macos
```

`main` に push すると CI（解析＋テスト）が回り、通れば
GitHub Pages に自動デプロイされる。
